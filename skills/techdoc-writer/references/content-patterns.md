# 内容范式：故障五段式、git diff 切分、术语表、速查表

## 1. 故障五段式（仅用于排障/混合型文档的故障章）

> **适用前提**：本式只在文档**确有调试/排障内容**时使用——素材里要有真实的"报错→定位→修复"链条。
> 纯指南/说明型文档（部署步骤、配置手册、架构说明、API/使用说明）通常**没有故障章**，
> 不要为了套骨架而把普通操作步骤硬塞进五段式，更不要编造不存在的"故障"。文档类型的判断见 SKILL.md ②。

> **纳入标准（机制坑 vs 代码错误）**：即使文档确有调试内容，故障章也只收**技术原理/机制层面**的坑——"理解了机制才能避免、踩了能学到可迁移知识"的问题（如：QoS 不兼容导致静默丢数据、CMake 在编译器探测阶段于临时子目录重解析相对 toolchain 路径而失败、异步 `dds_write` 的投递时机、`view_state` 是 instance 级且按访问评估）。
> **不要**把**简单代码错误**写进故障章或速查表——拼写错、变量/下标写错（如循环里把 `infos[i]` 误写成 `infos[0]`）、忘改某个常量/路径值、漏写一行——这类问题除了"改对"没有可迁移的原理价值，读者也不会拿它对照排查；它们最多在相应正文处一句带过，绝不单列故障小节。
> **判据**：把这条"故障"抽象成一句经验，它教的是**某项技术的工作机制**（收录），还是**只是某次手误**（不收）？

当文档有故障章时，每个问题/故障按固定五段组织。这个结构的价值：读者拿着自己的日志，能沿着 现象→解析→根因 的路径自己定位，而不是只抄解决方案。

```
x.y.1 故障现象     —— 日志/命令输出【原文】，放代码块。不要清洗、不要改写，
                     读者将来是拿自己的日志与此比对的。
x.y.2 逐条解析     —— 对日志中每条关键报错：加粗报错关键词，说明【谁】在调用
                     【谁】、期望得到什么、为什么失败（例如返回 -ENOIOCTLCMD
                     的机制）。一条报错一段。
x.y.3 根因分析     —— 机制层面的解释。最好能给出数值推导（例如
                     688+1920=2608 > 1920 → 判定越界），让结论可检验。
x.y.4 解决方案     —— 改了什么 + 为什么这样改 + 真实 git diff（见下节）。
x.y.5 验证结果     —— 命令 + 实测输出原文 + 判定标准（精确数字：
                     "46,656,000 字节 = 1920×1080×1.5×15 帧"）。
```

简单问题可以合并段落（如现象与解析合写），但"根因"和"验证"不可省。

## 2. 解决方案配真实 git diff

**原则**：文档里的代码必须可复核——直接从 commit 提取，不凭记忆重写。

按 hunk 切分到对应小节的方法（一个 commit 往往覆盖文档的多个小节）：

```python
import subprocess
from html import escape

def gitshow(commit, path):
    return subprocess.run(['git','show',commit,'--',path],
                          capture_output=True, text=True).stdout

def split_hunks(diff):
    """拆出 (---/+++ 头, [每个 @@ hunk 的文本])"""
    hdr, hunks, cur = [], [], None
    for ln in diff.split('\n'):
        if ln.startswith(('--- ','+++ ')): hdr.append(ln)
        elif ln.startswith('@@'):
            if cur: hunks.append('\n'.join(cur))
            cur = [ln]
        elif cur is not None: cur.append(ln)
    if cur: hunks.append('\n'.join(cur))
    return hdr, hunks

# 按关键词把 hunk 分到各小节，例如：
# 'VBLANK_MIN' in h        → vblank 小节
# 'of_property_read' in h  → probe 小节
# 其余                      → ioctl 小节
```

呈现方式：
- **飞书**：`<pre lang="Diff" caption="git diff <commit> — <主题>（节选）">`，Diff 高亮自动给 +/- 行着色。
- **Markdown**：```` ```diff ```` 围栏。
- caption/引导句标注来源 commit 短哈希，保证可追溯。
- 保留 `--- / +++ / @@` 头与上下文行，与 `git show` 输出一致。
- 与 diff 等价的"最终代码 + 行尾注释"形式仅在用户明确不要 diff 时使用。

### 同一文件被拆成多块时的标注

一个脚本/文件因讲解需要拆成多个代码块（如主流程、各辅助函数分开展示）时，**靠 caption 表达归属，不要另加说明框/callout 去解释"它们是同一个脚本"**——标题已经说清楚。

- 统一用 `<文件名> — <部分/函数名> — <一句说明>` 的 caption 格式，例如：
  - `board_detect.py — 主流程 — 采集/推理/回推`
  - `board_detect.py — letter_box — 等比缩放与灰边填充`
  - `board_detect.py — post_process — DFL 解码与置信度计算`
- 三段同前缀 `board_detect.py`，读者一眼看出同属一个文件。
- 拆块展示时仍要尊重真实定义顺序（被调用的函数应排在调用它的主循环之前），避免读者照块顺序拼接后报 `NameError`/`未定义`。
- **拆块讲解之后，必须给出一份完整、可直接运行的整脚本**（含全部 `import`、常量、所有被调用的函数定义、`if __name__ == '__main__'` 入口；任何 `# ...` 占位实现都要补成真代码），放在该主题末尾，或作为附件挂上；并注明"上方分块仅为讲解，可运行版以此完整脚本/附件为准"。分块是为讲解服务的，但读者最终要的是能跑的东西——**只给分块、不给完整脚本，等于把"按正确顺序拼接 + 补齐 import/常量 + 把省略的实现写全"甩给读者**，极易拼出 `NameError` 或残缺逻辑（典型：NMS 只剩 `# ... 按类做 NMS` 占位、`softmax` 被 `dfl` 调用却从未定义、整段缺 import 头）。完整脚本必须是真在目标环境跑通过的版本，不是把分块在脑子里拼一下。
- **引导语别复述附件/脚本的内容物**：附完整脚本（或任何附件、产物）时，引导句只需一句话点明"已在 X 环境验证、可直接运行的完整版，以此/附件为准"，**不要逐条罗列它内含哪些 import、常量、函数（"含 import、常量、softmax、letter_box、DFL 解码、NMS、主流程、__main__……"这种枚举是冗余噪音）**——读者要细节直接看脚本本身，文档复述一遍既啰嗦又会和脚本不同步。同理：表格/附件清单不必把每个字段、每个文件名再用散文复述一遍。

## 3. 术语表（附录）

三列：术语 | 全称 | 说明。规则：

- 正文出现过的**每个缩写**都要进表（CIF、ISP、3A、AE、D-PHY、V4L2…）。
- 全称写英文原文，必要时附中文（如 "AE（Auto Exposure）/ AWB（Auto White Balance）"）。
- 没有缩写的概念（如 "online 模式"）全称列写 "—"，靠说明列讲清。
- 说明列写它在本文档语境下的含义，不是泛义词典解释。

## 4. 故障速查总表

放在故障诊断章首，四列：故障现象 | 根本原因 | 解决方案 | 详见。

- 一行一个问题，覆盖正文出现过的全部问题（包括"预防项"——还没踩到但机制上必然踩的坑，标注"预防项"）。
- 只收**机制/原理层面**的问题；简单代码错误（手误、下标/常量写错、漏改值）不进表——判据见 §1 纳入标准。
- "详见"列填真实小节号，写完后逐个核对存在性。

## 5. 图表

- 整体架构/信号链路/流程优先用图。**飞书文档默认用飞书画板(whiteboard)呈现**——通过 **lark-whiteboard** skill 创建/更新画板(支持 PlantUML / Mermaid / 画板 DSL),**不要**把 ASCII 框图或 mermaid 源码当作文本/代码块贴进飞书文档。**仅本地 Markdown 输出**才用 ```mermaid 围栏或 ASCII。
- 图编号 `图 <章>-<序>`，编号行放图的紧邻位置。
- 表格前要有一句引导（"……差异如下："），不要裸表。

## 6. 前置物料的来源、落位与持久性（可复现性的高频盲区）

文档的作者是在一台**已经配好**的机器上写文档的，于是"早就放在那儿"的输入产物会被默写成"理所当然存在"，命令直接从"使用它"那一步起笔。但读者往往是在一台**全新或刚重烧**的设备上重走流程——卡住的地方，恰恰是这些没写出来的前置。

**判定标准**：正文里每一条会**消费输入产物**的命令（`pip install <whl>`、加载模型/固件、读某个配置文件、`source` 某脚本……），都要能回答三问：

| 维度 | 要写清的内容 | 反例（默认它在） | 正例 |
|---|---|---|---|
| **来源** | 该产物从哪来：仓库/SDK 相对路径、构建产物目录、下载地址 | `pip3 install rknn_toolkit_lite2-...whl` | "wheel 位于 SDK `external/rknn-toolkit2/.../packages/`，按目标 Python 版本选 cp 标签" |
| **落位** | 怎么到达执行命令的那台机器：`scp` / `adb push` / `cp` / 挂载 | （不提，读者无从下手） | `scp <相对路径>/xxx.whl root@board:/root/`，再到该目录用相对路径安装 |
| **持久性** | 重烧固件 / clean build 后还在吗；不在则标注重做方式并指向对应步骤 | （读者重烧后报 "No such file"/配置回滚，无从知道要重做） | "不随 rootfs 预置，重烧后丢失须重传（见 x.y）" / "重烧后该配置回滚为默认值，须重新改 3 处（见 x.y）" |

**持久性尤其要点名**——它是"重走流程"类文档最隐蔽的坑。常见会丢失/回滚的产物：板端临时安装的 wheel/pip 包、`/userdata` 下的模型与脚本、`/etc` 下被调过的配置文件（iqfile 等）、手动烧写的固件。凡是"装/改/传到设备上、但没进构建源"的东西，重烧后都会回到出厂态。

落地建议：
- 在"环境准备/部署"章节，把来源+落位作为**前置步骤**显式列出，排在"使用它"的命令之前，不要混在一行里。
- 把"重烧后会丢失/回滚"的产物在**故障诊断章**补一条（现象：`No such file`/配置失效；根因：未随构建源持久化；解决：从来源重新部署），并在**关键文件清单**里标注其来源与"重烧需重做"。
- 关键文件清单（附录）建议列：文件 | 位置/来源 | 是否随重烧持久 | 说明。
