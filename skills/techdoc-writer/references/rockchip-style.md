# Rockchip Developer Guide 风格骨架规范

本规范提炼自 Rockchip 官方《Rockchip_Developer_Guide_*_CN.pdf》系列文档的共同结构。默认骨架按此组织；用户指定其他参考文档时，按 SKILL.md ② 的四要素提炼法替换本规范的对应部分。

## 1. 整体结构

```
（封面信息 —— 可选，个人/团队内部文档常省略，见下文说明）
前言
  概述            一句话说明文档目的与适用对象
  平台支持        表格：芯片/内核版本/关键组件及版本
  读者对象        列出适用工程师角色
  修订记录        表格：版本号 | 作者 | 修改日期 | 修改说明
Chapter-1 系统概述
  1.1 子系统/架构简介（含整体框图，图 1-1）
  1.2 软硬件环境
  1.3 流程总览（阶段表，标注对应章节与验证标志）
Chapter-2 ~ Chapter-N 正文
  按依赖顺序组织：硬件 → 配置 → 适配 → 调试
  每章先概述本章目的，再分节展开
Chapter-N-1 故障诊断
  x.1 故障速查总表（现象/根因/解决/详见交叉引用）
  x.2+ 需要专门说明的疑难问题
Chapter-N 附录
  x.1 术语（术语 | 全称 | 说明 三列表格）
  x.2 版本控制记录（git log 原文）
  x.3 参考文档
```

**封面信息**（文件标识/发布版本/日期/密级/免责声明）是官方对外文档的要素；内部工程文档通常不需要，除非用户要求。先不加，用户要再补。

## 2. 编号体系

- 章：`Chapter-1 名称`（h1）
- 节：`1.1 名称`（h2）；小节：`1.1.1 名称`（h3）。不超过 4 层。
- 图表：`图 <章>-<序> 名称`，居中放在图下方；表格一般不编号但要有引导句。
- 跨章引用写"详见 x.y 节"，并保证目标真实存在。

## 3. 语言风格

- 客观、第三人称、工程化：写"驱动调用 regulator_bulk_enable() 时…"，不写"我们试了一下发现…"。
- 不用 emoji、不用口语化标点（"！！"等）。状态标注用文字：已完成/进行中。
- 数据精确：字节数、频率、行号、commit 哈希都写实测值。
- 解释"为什么"优先于罗列"做了什么"——官方文档的价值在于机制说明。

## 4. 章节内容组织模式

每个技术章节内部推荐顺序：

1. **改动/配置内容**：做了什么，配代码或 diff
2. **技术原理**：为什么这样做（机制层面）
3. **注意事项/冲突处理**：与现状的冲突、依赖的前置条件
4. **常见错误**：实施中容易犯的错（表格：错误内容/直接后果/修正）
5. **验证**：命令 + 预期输出，最好引用实测原文

不是每章都要五项齐全，但"原理"和"验证"尽量不缺——缺原理读者知其然不知其所以然，缺验证读者不知道自己做对没有。
