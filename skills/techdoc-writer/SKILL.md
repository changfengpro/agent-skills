# techdoc-writer：工程过程 → 官方风格技术文档

把一段真实的开发/调试经历（通常散落在会话记录、git 提交、终端日志里）整理成一份**别人拿来就能复现、出了问题能查到答案**的正式技术文档。这是本 skill 的全部目的——文档的读者是没有经历过这段调试的工程师，所以"过程中你知道但没写下来的东西"才是最有价值的内容。

## 总体流程

```
① 素材收集 → ② 确定风格骨架 → ③ 按骨架组织内容 → ④ 落地输出 → ⑤ 质量自检
```

每一步的产出都给用户过目的机会：骨架定了再写正文，正文写完再落地，避免大返工。

## ① 素材收集

文档的可信度来自一手素材。动笔前先收齐：

- **git 历史**：`git log --oneline` 找到相关提交；每个提交 `git show <commit>` 拿到真实 diff。解决方案必须配真实 diff（见 references/content-patterns.md 的切分方法），不要凭记忆重写代码。
- **日志原文**：板端 dmesg、终端报错、命令输出。故障章节必须引用**原文**（哪怕带乱序的串口回显），因为读者将来是拿自己的日志和文档比对的——改写过的日志对不上号。
- **会话中的因果链**：每个问题"为什么发生、怎么定位、为什么这样修"。这些通常只存在于对话里，是最容易丢的素材。
- **既有文档/附件**：用户已有的笔记、接线图、设备树附件等，整理时保留并归位到合适章节（飞书资源块的搬移方法见 references/feishu-notes.md）。

## ② 确定风格骨架

- **默认**：Rockchip Developer Guide 风格——前言（概述/平台支持/读者对象/修订记录）+ Chapter-N 编号正文 + 故障诊断章 + 附录（术语/版本记录/参考文档）。完整骨架规范读 **references/rockchip-style.md**。
- **用户指定参考文档时**：先读参考文档（PDF 读封面、前言、目录、一两个正文章节即可），提炼四要素——封面/前言要素、章节编号体系、图表编号规则、语言风格——再套用到目标文档。不必逐字模仿，抓结构和语气。
- 把拟定的章节目录先给用户确认，再写正文。

## ③ 按骨架组织内容

核心范式都在 **references/content-patterns.md**，写正文前必读。要点：

- **故障五段式**：现象（日志原文）→ 逐条解析 → 根因分析 → 解决方案 → 验证结果。这是整份文档最有价值的部分。
- **解决方案配真实 git diff**：按 commit 的 hunk 切分到对应小节，用 Diff 语法高亮。
- **术语表带全称**：缩写（CIF、ISP、3A…）必须展开英文全称，读者不一定有平台背景。
- **故障速查总表**：现象/根因/解决/详见 x.y 交叉引用，放故障诊断章首。
- **正式语言**：客观工程化表述、无 emoji、第三人称；数据要精确（"45M = 46,656,000 字节"而不是"大约 45M"）。

## ④ 落地输出

- **飞书云文档/wiki**（用户给了链接或要求写到飞书）：调用 **lark-doc** skill 操作，实操经验（XML 转义、block 操作顺序、资源块搬移、大改版的安全做法）读 **references/feishu-notes.md**。
- **本地 Markdown**（用户未指定或明确要本地文件）：直接写 .md，结构相同；git diff 用 ```diff 围栏。

## ⑤ 质量自检

交付前过一遍：

- [ ] 章节编号连续、目录层级 ≤ 4 层
- [ ] 每个故障五段齐全，日志是原文
- [ ] 每个解决方案有对应 diff，且 diff 来自真实 commit（可复核）
- [ ] 术语表覆盖正文出现的全部缩写，含全称
- [ ] 速查表的"详见"章节号真实存在
- [ ] 修订记录的版本/日期/作者已填
- [ ] （飞书）资源块（画板/附件）无丢失，outline 抓取验证结构
