# techdoc-writer：工程过程 → 官方风格技术文档

把一段真实的工程经历——可能是一次调试排障，也可能是一套部署/配置/适配流程（通常散落在会话记录、git 提交、终端日志里）——整理成一份**别人拿来就能复现、出了问题能查到答案**的正式技术文档。这是本 skill 的全部目的——文档的读者是没有亲历这段过程的工程师，所以"过程中你知道但没写下来的东西"（隐含的前置条件、为什么这么做、怎么验证对了）才是最有价值的内容。

## 总体流程

```
① 素材收集 → ② 确定风格骨架 → ③ 按骨架组织内容 → ④ 落地输出 → ⑤ 质量自检
```

每一步的产出都给用户过目的机会：骨架定了再写正文，正文写完再落地，避免大返工。

## ① 素材收集

文档的可信度来自一手素材。动笔前先收齐——**收什么取决于②判定的文档类型**：

- **git 历史（两类都要）**：`git log --oneline` 找到相关提交；每个提交 `git show <commit>` 拿到真实 diff。代码/配置改动必须配真实 diff（见 references/content-patterns.md 的切分方法），不要凭记忆重写。
- **既有文档/附件（两类都要）**：用户已有的笔记、接线图、设备树附件等，整理时保留并归位到合适章节（飞书资源块的搬移方法见 references/feishu-notes.md）。
- **前置物料的来源/落位/持久性（两类都要，指南型尤其关键）**：每条会消费输入产物的命令，背后那个产物从哪来、怎么到执行机器、重烧/clean build 后还在不在——这是"别人照着能复现"的命门，详见 references/content-patterns.md 第 6 节。

排障/混合型再额外收（指南型通常没有，别硬找）：

- **日志原文**：板端 dmesg、终端报错、命令输出。故障章节必须引用**原文**（哪怕带乱序的串口回显），因为读者将来是拿自己的日志和文档比对的——改写过的日志对不上号。
- **会话中的因果链**：每个问题"为什么发生、怎么定位、为什么这样修"。这些通常只存在于对话里，是最容易丢的素材。

指南/说明型再额外收（这些才是指南的主干）：

- **正向流程的每一步**：操作顺序、每步的命令与预期回显、步骤间的依赖（"X 必须在 Y 之前")。
- **验证标准**：怎么判断这一步/整体做对了——命令 + 期望输出 + 精确判据（端口监听、服务 `active (running)`、产物大小非零等）。
- **配置项的含义与取值**：关键配置字段为什么填这个值、可选范围、与硬件/平台的绑定关系。

## ② 确定风格骨架

- **先判断文档类型**——决定要不要故障诊断章：
  - **排障/调试型**（bring-up 踩坑、问题定位、故障复盘）：以"问题→根因→修复"为主线，**故障五段式是核心**，必含故障诊断章。
  - **指南/说明型**（部署步骤、配置手册、架构说明、API/使用说明、操作流程）：以"怎么做对"为主线，**通常没有故障章，也不要硬凑五段式**。把内容按操作步骤/模块/概念组织即可。
  - **混合型**：正文是指南，但调试中确实踩了值得记录的坑——正文照指南组织，把这些坑单独收进一个故障诊断章，不要把每个普通步骤都套五段式。
  - 判断依据是**素材里有没有真实的"报错→定位→修复"链条**：有才写故障章，没有就别为了套骨架而编故障。
  - 入选故障章的坑要再过一道筛：只收**技术原理/机制层面**的坑，简单代码错误（手误、下标/常量写错、漏改某个值）不进故障章，最多正文一句带过——详见 references/content-patterns.md §1 纳入标准。
- **默认骨架**：Rockchip Developer Guide 风格——前言（概述/平台支持/读者对象/修订记录）+ Chapter-N 编号正文 +（排障/混合型才加）故障诊断章 + 附录（术语/版本记录/参考文档）。完整骨架规范读 **references/rockchip-style.md**。
- **用户指定参考文档时**：先读参考文档（PDF 读封面、前言、目录、一两个正文章节即可），提炼四要素——封面/前言要素、章节编号体系、图表编号规则、语言风格——再套用到目标文档。不必逐字模仿，抓结构和语气。
- 把拟定的章节目录先给用户确认，再写正文。

## ③ 按骨架组织内容

核心范式都在 **references/content-patterns.md**，写正文前必读。要点：

- **故障五段式（仅排障/混合型文档的故障章用）**：现象（日志原文）→ 逐条解析 → 根因分析 → 解决方案 → 验证结果。文档若有故障章，这是它最有价值的部分；纯指南/说明型文档没有故障章，跳过本式，按操作步骤/模块组织正文即可。
- **解决方案配真实 git diff**：按 commit 的 hunk 切分到对应小节，用 Diff 语法高亮。
- **术语表带全称**：缩写（CIF、ISP、3A…）必须展开英文全称，读者不一定有平台背景。
- **故障速查总表**：现象/根因/解决/详见 x.y 交叉引用，放故障诊断章首。
- **前置物料可复现**：每条"消费输入产物"的命令，都要写清该产物的**来源**（仓库/SDK 相对路径、构建产物、下载地址）、**落位**（如何 `scp`/`adb push`/`cp` 到执行命令的那台机器）、**持久性**（重烧固件 / clean build 后是否还在；不在就标注"须重传/重新生成"并指向对应步骤）。文档默认从作者已配好的机器视角写，"本来就在"的前置文件最容易漏——而重走流程的读者恰恰卡在这里。详见 references/content-patterns.md 第 6 节。
- **正式语言**：客观工程化表述、无 emoji、第三人称；数据要精确（"45M = 46,656,000 字节"而不是"大约 45M"）。

## ④ 落地输出

- **飞书云文档/wiki**（用户给了链接或要求写到飞书）：调用 **lark-doc** skill 操作，实操经验（XML 转义、block 操作顺序、资源块搬移、大改版的安全做法）读 **references/feishu-notes.md**。**图（架构/流程/信号链路）默认用飞书画板**：通过 **lark-whiteboard** skill 创建/更新画板（PlantUML/Mermaid/DSL），不要把 ASCII 框图或 mermaid 源码当文本块贴进飞书文档。
- **本地 Markdown**（用户未指定或明确要本地文件）：直接写 .md，结构相同；git diff 用 ```diff 围栏。

## ⑤ 质量自检

交付前过一遍：

- [ ] 章节编号连续、目录层级 ≤ 4 层
- [ ] （有故障章时）每个故障五段齐全，日志是原文；纯指南型文档无此项，不必为凑结构编故障
- [ ] （有故障章时）每条故障都是机制/原理层面的坑；简单代码错误（手误、下标/常量写错、漏改值）未混入故障章或速查表
- [ ] 每个解决方案/关键改动有对应 diff，且 diff 来自真实 commit（可复核）
- [ ] 每条消费输入产物的命令都写清来源/落位；重烧或 clean build 后会丢失/回滚的产物（wheel、模型、固件、被覆盖的配置文件等）已标注重做方式
- [ ] 被拆成多块讲解的脚本，末尾或附件给出了一份**完整可运行**的整脚本（import/常量/全部函数/入口齐全，`# ...` 占位已补实，且确为目标环境跑通过的版本）
- [ ] （指南/说明型）每个操作步骤都有对应的验证标准——命令 + 期望输出/精确判据，读者能自己确认这步做对了
- [ ] 术语表覆盖正文出现的全部缩写，含全称
- [ ] （有故障章时）速查表的"详见"章节号真实存在；指南型文档无速查表，跳过
- [ ] 修订记录的版本/日期/作者已填
- [ ] （飞书）架构/流程/信号链路图用飞书画板呈现，而非 ASCII/纯文本代码块
- [ ] （飞书）资源块（画板/附件）无丢失，outline 抓取验证结构
