# reusable-solution-doc:具体问题 → 通用可复用解决方案

把一次刚排掉的具体问题,提炼成一份**别人换个工程、换个文件名也能照着做**的通用技术文档。读者是没有亲历这次过程、但碰到了同一类问题的开发者,所以文档的价值在于:把"问题的类别、根因机制、通用解法"讲清楚,而不是复述"我这次的文件叫什么、库叫什么"。

## 何时用本 skill,何时用 techdoc-writer

| | reusable-solution-doc(本 skill) | techdoc-writer |
|---|---|---|
| 目标 | 把「这一类」问题做成通用参考 | 把「这一次」经历做成可交付文档 |
| 专有名词 | **剥离**,换占位符/类别 | **保留**,真实文件/库/平台名 |
| 素材 | 抽象后的根因与解法 | git diff、原始日志、设备树等一手料 |
| 风格 | 简明问题解决式 | 官方手册风格(Rockchip 骨架等) |
| 落位 | 本地 Markdown(默认 `~/文档`) | 飞书云文档或本地 |

判断:用户强调"**通用 / 其他人也能参考 / 不要具体名字**" → 本 skill;强调"**把这次的过程 / bring-up / 调试记录沉淀下来**" → techdoc-writer。

## 硬性风格约定(本项目用户固定偏好)

- **措辞严肃偏技术,禁用任何比喻、修辞、煽情**;第三人称客观陈述;无 emoji。
- **去具体化是本 skill 的核心**:正文不出现具体工程名、文件名、库名、私有路径;用占位符(`<构建目录>`、`<依赖库包含目录>`)和类别词("某代码生成器生成的头""被 gitignore 屏蔽的依赖目录")替代。
- **相对路径优先,绝不硬编码可变量**(承 changfengpro 规范1):路径用 `${变量}`、`<占位符>` 或相对形式,不写死绝对路径/IP/端口/设备号。
- **可操作但通用**:给真实可执行的命令和配置片段,但其中的名字用占位符,读者替换即用。
- **标注适用边界**:明确该方案在什么工具 / 平台 / 版本 / 生成器下成立(例:"`CMAKE_EXPORT_COMPILE_COMMANDS` 仅 Makefile/Ninja 生成器支持")。

## 固定文档结构

按下列骨架组织(可按主题增删,但顺序与意图保持):

1. **标题 + 元信息**:一行场景定位;适用场景 / 编辑器或工具 / 日期。
2. **问题现象**:读者用来对号入座的可观察症状(报错、行为)。列出该问题的几种典型触发情形。
3. **根因**:讲机制,不讲个例。多个并列原因时用**对照表**(类型 → 失败原因)。
4. **解决步骤**:编号步骤,每步给命令 / 配置片段(占位符化);关键前置条件单独标"(关键)"。
5. **验证清单**:怎么确认修好了——可勾选的判据。
6. **维护要点**:后续什么操作会让它再次失效、需要重做哪步(如"改了生成器输入要重新构建")。
7. **备注**:相关但非主线的坑 / 噪声(如某扩展的无害报错),说明可忽略或怎么消除。
8. **备选方案**:次优解 + **明确写出不推荐的理由**,避免读者误选。
9. **(可选)其他工具 / 引擎的等价做法**:同一问题在替代工具下的等价配置。

模板见 `references/template.md`,可直接复制填充。

## 去具体化操作清单

把一手材料逐项抽象——这是从"调试记录"变成"通用参考"的关键动作:

- 具体文件名 → 文件**类别**(`foo_generated.h` → "构建期生成的头")。
- 具体库名 / 工程名 → **去掉或泛化**("CycloneDDS 的 `dds/dds.h`" → "位于非标准目录的依赖头")。
- 私有绝对路径 → **占位符 / 相对形式**(`/home/x/proj/build/host` → `${workspaceFolder}/<构建目录>`)。
- 具体配置命名 → **通用命名**(preset `arm-rv1126b`/`host` → `cross`/`native`)。
- 个例数值 → 保留有普适意义的,删与个例强绑定的。
- 自检:把工程名、用户名、机器名、私有路径全文搜一遍,确认正文里没有残留。

## 落地与命名

- 默认落本地 Markdown(用户常用目录 `~/文档`);除非用户要求,不上飞书。
- 命名沿用用户习惯:`主题_细节_日期.md`(日期 `YYYY-MM-DD`,取当天)。
- 不与已有同主题文档重复;若是对旧文档的通用化重写,产出新文件后删除旧的具体版(经用户确认)。

## 质量自检

交付前逐条核对:

- [ ] 正文无具体工程 / 文件 / 库 / 用户 / 机器名,占位符一致且自解释。
- [ ] 无比喻、无 emoji、第三人称。
- [ ] 命令 / 配置片段可操作,路径无硬编码绝对值。
- [ ] 标注了适用边界(工具 / 平台 / 版本)。
- [ ] 结构含:现象 → 根因 → 步骤 → 验证 → 维护;备选方案附不推荐理由。
- [ ] 换一个工程套用此文档,步骤仍成立。
